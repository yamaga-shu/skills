引数: $ARGUMENTS

引数の先頭の数字を issue 番号として扱う。残りがあれば、重点的に詰めて描く対象（集約、状態遷移、処理の流れなど）として扱う。
issue 番号が無ければ、始める前にユーザーに聞く。

開始前に Skill ツールで "grilling"、"doc-convention"、"domain-modeling"、"github-convention" を 1 つずつ読み込む。
同じセッションで既に読み込んだものは読み直さない。1 回の呼び出しに複数の名前を渡さない。

- grilling がパターンを詰めるインタビューの進め方を決める
- doc-convention が用語集の場所と、同じ事実を複数箇所に書かない原則を決める
- domain-modeling が用語集の読み方、詰める途中で用語集を直す規律、ADR を書く基準を決める
- github-convention が issue の読み方、本文の編集の仕方、改訂の記録の仕方を決める

## 流れの中の位置

grill-with-docs が「何をどう振る舞わせるか」を「決定」に固め、このスキルがその決定を実現する構造をどのパターンで組むかを詰めて用語集の言葉で図にし、plan-from-issue がその図を前提に計画を立てる。
図示するほどの構造が無い issue や、grill-with-docs が書いた「設計」で足りる issue では使わない。

図は issue の本文に置き、リポジトリのファイルにはしない。
issue はある時点の判断の記録なので、後にコードが変わって図と食い違っても、ドキュメントの誤りとしては扱われない。

## 読むもの

- issue。github-convention の「issue の読み方」に従って本文とコメントを読む。
  「決定」「スコープ」「実装時に決めること」、既存の「設計」、親 issue の「決定」を把握する
- 用語集。場所は doc-convention の正本の表と AGENTS.md の上書きに従う。
  複数コンテキストなら、issue が属するコンテキストの用語集を読む
- ADR。ルートのものと、issue が属するコンテキストのものを読む。既に決まっているパターンの前提になり、図の補足からリンクする候補になる

次のときは詰めずに止める。

- 用語集が無い。`/grill-with-docs <番号>` で用語集を作ってから戻るよう案内する
- 「決定」が空、または振る舞いが決まっていない。何を実現するかが決まらなければ構造は決められない。
  足りない論点を挙げて `/grill-with-docs <番号>` を案内する

## コードを調べる

このスキルを呼ぶ時点で「決定」はまだ実装されていない。
図は「決定」を実装した後の姿を描くので、「決定」の構造がコードに無いことは食い違いではなく前提である。
コードを読むのは、「決定」が触れる既存の構造を知り、既存の部分と足す部分を区別して描くため、
そしてパターンの推奨を既存のコードの形に揃えるためである。

「含む」に挙がった範囲が触れる既存の構造を読む。
規模が大きければサブエージェントに調べさせ、報告を待つ間に依存しないラウンドを進める。

- 用語に対応する既存の型、モジュール、テーブル
- 既存の用語同士の関係。まとめて読み書きする所有関係か、ID だけの参照か、一方が他方を生成するか
- 既存の状態と遷移
- 「決定」が変える既存の処理の流れ
- 既存のコードが採っているパターン。集約の切り方、リポジトリやサービスの置き方、イベントの使い方など

「決定」が既にあるものとして扱っている構造がコードに無い、または違う形であるなら表に出し、ユーザーに問う。
これから足す構造の話ではなく、決定の前提が崩れている場合だけである。

## パターンを詰める

「決定」は何を実現するかを言い、どの構造で実現するかは言っていないことが多い。
その隙間を grilling の設計ツリーとして捉え、ラウンドの書式で聞く。
論点の源は次の観点である。「決定」と「含む」が触れる範囲について、各観点で答えが一つに決まっていないものが質問になる。

| 観点 | 典型的な論点 |
| --- | --- |
| 境界 | どの用語を集約ルートにするか。関係を所有で持つか ID 参照で持つか。どのコンテキストが持つか |
| 表現 | エンティティか値オブジェクトか。状態を属性で持つか型で分けるか。振る舞いの差を条件分岐で持つか State や Strategy で分けるか |
| 振る舞いの置き場 | 集約のメソッドか、ドメインサービスか、アプリケーションサービスか。不変条件をどこで守るか |
| 連携 | 集約やコンテキストの間を直接呼ぶか、ドメインイベントで結ぶか。同期か非同期か。整合性をトランザクションで取るか結果整合で取るか |
| 永続化と取得 | リポジトリの単位。ファクトリの要否。読み取りを書き込みモデルと分けるか |

ラウンドの進め方は grilling に従う。前提の順は概ね表の上から下で、境界が決まらないうちは表現と置き場は聞けない。

- 各質問には候補のパターンを 2〜3 個挙げ、それぞれが「決定」の具体的なシナリオでどう振る舞うかを一文で示す。
  domain-modeling の「具体的なシナリオで議論する」に従い、境界を突くシナリオを選ぶ
- 推奨は、既存のコードで使われているパターンに揃えるのを基本にする。
  外すときは、揃えると「決定」のどこが満たせないかを言う
- コードから答えが一つに決まる事柄は質問にせず、前提として述べる。既存の構造が既に決めている
- 「決定」、親 issue の「決定」、ADR が既に決めているパターンは聞き直さない
- ユーザーが実装に委ねると答えた論点は「実装時に決めること」に回し、図にはその構造を描かない
- 答えが「決定」の振る舞いやスコープを変える論点は、このスキルでは決めない。
  ラウンドの中で指摘し、その論点を避けて図を描けるなら補足に書き、描けなければ止めて `/grill-with-docs <番号>` を案内する

通常は 1〜2 ラウンドで済む。フロンティアが空になってから図を描く。

## 用語集との矛盾を直す

パターンを詰める途中と図を描く途中で用語集と食い違いが見つかったら、その場で用語集を直す。
図は用語集の言葉で描くので、用語集が曖昧なまま図だけを整えるわけにはいかない。
直し方は domain-modeling と CONTEXT-FORMAT.md に従い、ユーザーの承認を待たずに `CONTEXT.md` に反映する。
既に用語集が正しく書かれていれば何もしない。

- **用語集に無い概念**が「決定」やコードにある。CONTEXT-FORMAT.md の基準で判断し、
  コンテキスト固有の概念なら用語集に足してから図に使う。
  一般的なプログラミング概念なら載せず、`OrderRepository` のように用語との組み合わせで名付ける
- **既存の用語について、用語集の定義とコードの振る舞いが食い違う。** どちらが正しいかをユーザーに問い、
  用語集が違うなら定義を書き直す。コードが違うなら定義は変えず、この issue で直すのか、別の issue に切り出すのかを問い、
  直す旨を図の補足に書く。「決定」で振る舞いを変える用語は、変えた後の振る舞いで定義する
- **用語集の定義と「決定」の言葉が食い違う。** どちらが正しいかをユーザーに問い、
  用語集が違うなら定義を書き直す。「決定」が違うなら、github-convention に従って本文の「決定」の言葉を用語集に合わせ、改訂のコメントを残す
- **同じ概念に複数の言葉が使われている。** 用語集、「決定」、コードの間で呼び名が割れていれば、
  CONTEXT-FORMAT.md の「態度を決める」に従って一つを選び、残りを `_避ける_` に加える
- **定義が曖昧で、図のノードや辺の意味が一つに決まらない。** 図で問われた区別（所有か参照か、状態の境界など）を定義に足し、1〜2 文に収める

## 図を描く

[DIAGRAM-FORMAT.md](./DIAGRAM-FORMAT.md) に従う。
このファイルは自動では読み込まれないため、図を描く前に必ず読むこと。

- 「決定」を実装した後の姿を、詰めたパターンのとおりに描く。既存の部分とこの issue で足す部分は、DIAGRAM-FORMAT.md に従い文で区別する
- 描く範囲は「含む」と、それが触れる既存の構造に限る。コンテキスト全体は描かない
- 描くのは「決定」に入った構造と、このセッションで決めたパターンだけにする。
  「実装時に決めること」に残した構造は描かず、補足の文で実装時に決めると示す
- 既存の「設計」があれば、判断の理由を述べた文は残し、図を差し替える

提示する前に、mermaid が描画できるかを確かめる。
`mmdc` などの描画ツールが使えるなら通し、構文エラーがあれば直す。使えなければ、描画を確かめていないことを提示に添える。

## 提示と書き込み

次をまとめて提示し、ユーザーの承認を得てから issue に書く。承認前に書かない。

- 「設計」節の全文
- 「決定」に加える項目。詰めたパターンのうち候補が割れた論点は、ラウンドで挙げた候補を「採らなかった選択肢との比較」の表にする
- 「実装時に決めること」に加える項目
- ADR の草稿。詰めたパターンのうち、domain-modeling の「ADR は控えめに提案する」の三つの条件をすべて満たすものだけ
- 直した用語の一覧。用語集は「用語集との矛盾を直す」に従って既に直してあるので、これは報告である

承認されたら、github-convention に従って本文の「決定」「設計」「実装時に決めること」を編集し、改訂のコメントを残す。
本文に「設計」節が無ければ、ISSUE-FORMAT.md の順序に従って「スコープ」の後に足す。
ADR は ADR-FORMAT.md に従って書き、比較と経緯の置き場所としてこの issue へリンクする。

書き終えたら、直した `CONTEXT.md` と書いた ADR があればそのファイルを示し、`/plan-from-issue <番号>` を案内して終える。
`CONTEXT.md` と ADR のコミットはしない。
