引数: $ARGUMENTS

引数の先頭の数字を issue 番号として扱う。残りがあれば、インタビューで重点的に詰めるテーマとして扱う。
issue 番号が無ければ、始める前にユーザーに聞く。

開始前に Skill ツールを 4 回呼び、"grilling"、"doc-convention"、"domain-modeling"、"github-convention" をこの順にそれぞれ読み込む。1 回の呼び出しに複数の名前を渡さない。

- grilling がインタビューの進め方を決める
- doc-convention が書く場所と、同じ事実を複数箇所に書かない原則を決める
- domain-modeling が用語集と ADR を書く規律を決める
- github-convention が issue 本文の書き方と、改訂の記録の仕方を決める

## 書く時期

用語集（`CONTEXT.md`）は domain-modeling に従い、用語が確定したその場で更新する。
ADR と issue 本文への反映は、フロンティアが空になり、ユーザーが共通理解に達したと確認してから行う。

## issue への記録

issue を検討の経緯の正本として扱う。

- **開始時**に、既に決まっていることを読んでから設計ツリーを組む。
  - `gh issue view <番号> --json title,body,comments,parent` で本文とコメントを読み、設計ツリーの出発点にする。
    `--comments` は非対話環境ではコメントだけを出力し本文が落ちるため使わない。
  - 用語集を読む。ルートに `CONTEXT-MAP.md` があればそれを読み、issue が属するコンテキストの `CONTEXT.md` を読む。
    無ければルートの `CONTEXT.md` を読む。どちらも無ければ用語集は未作成として進める。
    domain-modeling の「用語集と照らして異議を唱える」は、ここで読んだ用語が前提になる。
  - 既存の ADR をすべて読む。ADR にある決定は確定した前提として扱い、
    ユーザーが覆さない限り聞き直さない。覆すなら、その ADR を `superseded` にして新しい ADR を書く。
    置き場所は doc-convention の「正本の表」に従う。
  親 issue があれば、その本文も読み、親の「決定」と「含まない」を確定した前提として扱う。
  親と矛盾する回答が出たら、その場で指摘し、sub-issue ではなく親を改訂するかをユーザーに問う。
  「決定」に書かれた事柄は確定した前提として扱い、ユーザーが覆さない限り聞き直さない。
  ただし下流の回答が既存の決定と矛盾したら、その場で指摘して聞き直す。
  「実装時に決めること」と「注記」は質問の候補にする。
  本文が github-convention の ISSUE-FORMAT.md の構成でなければ、本文全体を出発点にする。
  コメントに残る改訂の理由は、同じ論点を再び聞かないため、また覆すときに前回の理由を踏まえるために使う。
- **フロンティアが空になったら**、セッションで確定した決定をまとめて issue 本文に反映する。
  ラウンドごとには書かない。
  本文の編集と改訂コメントの残し方は github-convention に従う。
  本文が ISSUE-FORMAT.md の構成でなければ、無い節だけを足して書き、既存の文は書き換えない。
  判断が割れた論点は、ラウンドで提示した選択肢を「採らなかった選択肢との比較」の材料にする。
  答えが出た項目は「実装時に決めること」から「決定」へ移す。
  ユーザーが実装に委ねると答えた論点は「実装時に決めること」に加える。
  セッションでやらないと決めた事柄は、理由を添えて「含まない」に加える。
- ADR を書くときは、比較と経緯の置き場所としてその issue へリンクする。
