# 進め方の区分

すべての issue に全工程を通すと、設計判断を含まない小さな変更にも、インタビューと独立セッションの時間がかかる。
この規約は、変更の正しさを確かめる工程を残したまま、進め方の工程を変更の大きさと危うさに応じて省けるようにする。
区分の定義と、区分ごとに通す工程の正本はこのスキルである。他のスキルは区分を読んで従い、定義を書き直さない。

## どの区分でも省かない工程

次の工程は区分によらず通す。
いずれも変更の正しさと安全性を確かめる工程であり、省くと不具合や脆弱性を PR より前に見つけられなくなるため。

- 完了条件を外から判定できる形で書いた issue
- コミットごとの確認コマンド、またはリポジトリのテストと lint
- [code-review](../code-review/SKILL.md) の `--fix` による差分のレビューと、修正後の検証
- 完了条件の確認と、その結果を PR の「確認方法」に残すこと
- PR のタイトルと本文の全文をユーザーが承認すること

ユーザーがこれらの工程を省くよう求めたときは、省くと何を確かめられなくなるかを一文で伝える。
それでも省くなら従い、省いた工程と、ユーザーの判断で省いたことを PR の「確認方法」に書く。

## 区分の判定

大型、軽微の順に当てはめ、どちらにも当てはまらなければ通常にする。
迷ったら上の区分（大型の側）にする。

### 大型

次のどれかに当てはまる issue である。変更行数が小さくても大型にする。

- 新しい設計判断を含む。用語集に無い概念を導入する、ADR の条件を満たす判断をする、既存の決定を変える、のいずれか
- 認証、認可、決済、個人情報、秘密情報の扱いに触れる
- スキーマの変更やデータの移行など、マージ後に取り消しにくい変更を含む
- 外部に公開しているインターフェース（API、CLI の引数、設定ファイルの形式）を変える
- 変更行数（追加と削除の合計）の見積もりが 1000 行を超える

### 軽微

大型に当てはまらず、次のすべてを満たす issue である。

- どう作るかが、issue のリード文と完了条件から一通りに決まる
- 変更が一つのモジュールの中に収まる
- 変更行数の見積もりが 100 行以下である

文言や表示の修正、設定値の変更、原因と直し方が分かっているバグの修正、パッチバージョンの依存更新、ドキュメントの修正が典型である。

### 通常

大型にも軽微にも当てはまらない issue である。
既存の決定と用語の範囲で作れる機能追加や修正がここに入る。

## 区分ごとの工程

| 工程 | 軽微 | 通常 | 大型 |
| --- | --- | --- | --- |
| `grill-to-issue` | 通す | 通す | 通す |
| `grill-with-docs` | 通さない | issue の「決定」が計画に足りないときだけ通す | 通す |
| `domain-design` | 通さない | 通さない | 任意 |
| `plan-from-issue` | 通さない。実装時にコミットの分け方を決め、PR 本文に残す | 通す | 通す |
| `code-review --fix` | 実装セッションで行う | 独立セッションで行う | 独立セッションで行う |
| `simplify` | 通さない | 通さない | 独立セッションで行う |

表で「通さない」とした工程も、ユーザーが求めれば通す。

## 区分の記録と変更

- 区分は `grill-to-issue` が判定して提案し、ユーザーが決める。
  決めた区分と、その区分にした理由の一行を issue 本文の「進め方」節に書く。
- 「進め方」節が無い issue は大型として扱う。この規約を入れる前に立てた issue の進め方を変えないため。
- 作業の途中で、より上の区分の条件に当てはまると分かったら、作業を止めてユーザーに区分の引き上げを提案する。
  引き上げたら github-convention に従って本文を改訂し、引き上げた区分の工程のうち未実施のものから再開する。
- 区分を下げるのは、ユーザーが求めたときだけである。下げたら同じく本文を改訂する。
