# CONTEXT.md の書式

## 構造

```md
# {コンテキスト名}

{このコンテキストが何で、なぜ存在するかの 1〜2 文の説明}

## 用語

**注文 (Order)**:
{用語の 1〜2 文の説明}
_避ける_: 購入、取引

**請求書 (Invoice)**:
納品後に顧客へ送る支払い請求。
_避ける_: 請求、支払い依頼

**顧客 (Customer)**:
注文を行う個人または組織。
_避ける_: クライアント、購入者、アカウント
```

## ルール

- **態度を決める。** 同じ概念に複数の言葉があるなら、最良の一つを選び、残りを `_避ける_` に列挙する。
- **定義は短く。** 最大 1〜2 文。何を _するか_ ではなく何 _であるか_ を定義する。
- **正式用語とコード上の識別子が違うなら併記する。** 日本語の用語が正式で、コードでは英語の識別子を使う場合、`**注文 (Order)**` のように書く。どちらか一方だけで済むなら括弧は付けない。
- **このプロジェクトのコンテキストに固有の用語だけを載せる。** 一般的なプログラミング概念（タイムアウト、エラー型、ユーティリティのパターン）は、プロジェクトが多用していても載せない。用語を足す前に「このコンテキスト固有の概念か、一般的なプログラミング概念か」を問い、前者だけを載せる。
- **自然なまとまりが見えたら小見出しで分ける。** すべての用語が一つのまとまりに収まるなら、平坦な一覧でよい。

## 単一コンテキストと複数コンテキスト

**単一コンテキスト（多くのリポジトリ）:** ルートに `CONTEXT.md` を一つ置く。

**複数コンテキスト:** ルートの `CONTEXT-MAP.md` に、各コンテキストの名前、場所、相互の関係を書く。

```md
# コンテキストマップ

## コンテキスト

- [Ordering](./src/ordering/CONTEXT.md): 顧客の注文を受け付け、追跡する
- [Billing](./src/billing/CONTEXT.md): 請求書を生成し、支払いを処理する
- [Fulfillment](./src/fulfillment/CONTEXT.md): 倉庫でのピッキングと出荷を管理する

## 関係

- **Ordering → Fulfillment**: Ordering が `OrderPlaced` イベントを発行し、Fulfillment がそれを受けてピッキングを開始する
- **Fulfillment → Billing**: Fulfillment が `ShipmentDispatched` イベントを発行し、Billing がそれを受けて請求書を生成する
- **Ordering ↔ Billing**: `CustomerId` と `Money` の型を共有する
```

どちらの構造かはスキルが推測する。

- `CONTEXT-MAP.md` があれば、それを読んでコンテキストを見つける
- ルートの `CONTEXT.md` だけがあれば、単一コンテキスト
- どちらも無ければ、最初の用語が確定したときにルートの `CONTEXT.md` を遅延して作る

複数のコンテキストがあるときは、いまの話題がどのコンテキストに属するかを推測する。不明なら聞く。
