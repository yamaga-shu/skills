# ADR の書式

置き場所は doc-convention の「正本の表」に従う。ファイル名は `0001-slug.md`、`0002-slug.md` のように連番を付ける。

## テンプレート

```md
# {決定の短い題名}

{1〜3 文: どういう文脈で、何を決め、なぜか}
```

これだけである。ADR は一段落でよい。価値は、決定が _あった_ ことと _なぜ_ かを記録することにあり、節を埋めることにはない。

## 任意の節

本当に価値を足すときだけ付ける。多くの ADR には要らない。

- **Status** の frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）: 決定を見直すことがあるなら有用
- **検討した選択肢**: 却下した理由が自明でない選択肢に限り、1 行ずつ書く。比較の詳細と検討の経緯は issue に書き、ADR からはリンクする（正本は issue。doc-convention 参照）
- **影響**: 自明でない下流への影響を明示する必要があるときだけ

## 採番

ADR の置き場所を走査し、最大の番号に 1 を足す。

## 条件を満たす決定の例

ADR を提案する三つの条件は SKILL.md の「ADR は控えめに提案する」が正本である。以下はその条件を満たす典型例。

- **アーキテクチャの形。** 「モノレポにする」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres に投影する」
- **コンテキスト間の連携パターン。** 「Ordering と Billing は同期 HTTP ではなくドメインイベントで通信する」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、差し替えに四半期かかるものだけ
- **境界と範囲の決定。** 「顧客データは Customer コンテキストが所有し、他のコンテキストは ID だけで参照する」。明示的な「やらない」は「やる」と同じくらい価値がある
- **当然の道からの意図的な逸脱。** 「X の理由で ORM ではなく手書き SQL を使う」。まともな読み手が逆を想定するもの。次のエンジニアが意図的なものを「修正」するのを防ぐ
- **コードに現れない制約。** 「コンプライアンス要件で AWS を使えない」「パートナー API の契約で応答時間は 200ms 未満」
- **却下理由が自明でない代替案。** GraphQL を検討して微妙な理由で REST を選んだなら記録する。さもないと半年後に誰かがまた GraphQL を提案する
