# Git 運用規約

AI エージェントが Git 操作を行う際に従う規約。
人間の運用を縛るものではなく、AI に一貫した振る舞いをさせることを目的とする。

## 前提

- **言語は既存のコミット履歴に合わせる。** 履歴が無い、または混在している場合は日本語で書く。
  issue・PR の言語もこれに揃える（github-convention はこの規則を参照する）。
- 以下は既定値で説明する。リポジトリで変える場合は、ルートの AGENTS.md に「Git 規約」の節を置き、
  変える項目だけを書く。書かれていない項目は既定値に従う。

  ```markdown
  ## Git 規約
  - コミットメッセージの言語: 英語
  - ブランチ名: `<type>/<slug>`
  ```

- **始める前にルートの AGENTS.md を読む。** 自動で読み込まれる保証はないので、明示的に読む。
  「Git 規約」の節があれば、そこに書かれた項目だけ既定値を置き換える。

## type と scope

変更の種類を表す `type` を、ブランチ名の先頭とコミット件名の先頭に置く。両者で同じ語を使う。
以下は例示であり、網羅的な許可リストではない。適切なものがなければ他の語を使ってよい。
リポジトリの履歴で既に使われている type があれば、それを優先する。

| type | 用途 |
| --- | --- |
| `feat` | 機能の追加 |
| `fix` | バグの修正 |
| `docs` | ドキュメントの変更 |
| `refactor` | 挙動を変えないコードの整理 |
| `test` | テストの追加・修正 |
| `chore` | ビルド設定や依存関係など、上記に当てはまらない雑務 |

`scope` は変更が及ぶ範囲を表す任意の語で、コミット件名で `<type>(<scope>): ` の形に置く。
ブランチ名には入れない。

- リポジトリの履歴で既に使われている scope があれば、それに揃える。
- 無ければ、ディレクトリ名、パッケージ名、モジュール名のような、変更箇所を一語で特定できる名前を使う。
- 変更がリポジトリ全体に及ぶ、または一語で特定できないときは scope を省き `<type>: ` と書く。

```
feat(api): ...        # api ディレクトリ配下の機能追加
fix(auth): ...        # auth モジュールの修正
docs: ...             # 全体に及ぶので scope を省く
```

## ブランチ

既定ブランチへ直接コミットしない。作業は必ずブランチを切って PR 経由でマージする。
既定ブランチは設定ではなく検出する。次を上から順に試し、成功した最初の結果を使う。すべて失敗したらユーザーに聞く。

```bash
git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|^origin/||'
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
git remote set-head origin -a && git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|^origin/||'
```

### 命名

```
<type>/<ユーザー名>/<issue番号>/<slug>
```

- `<type>` — 上の type と scope 節に従う。scope は入れない。
- `<ユーザー名>` — 作業者を識別できる短い名前。決め方は次節。
- `<issue番号>` — 対応する issue の番号。**issue がない作業ではこの階層ごと省略してよい。**
- `<slug>` — 内容を表す英小文字ケバブケース。

```
feat/alice/3/git-convention     # issue #3 に対応
docs/alice/readme-typo          # issue なし
```

### ユーザー名の決め方

`alice` 程度の長さの英小文字を、次の順で決める。

1. **その人が過去に切ったブランチがあれば、それに揃える。**
   リモートブランチの先端コミットの author を `git config user.name` と突き合わせて探す。

   ```bash
   git fetch --prune
   git for-each-ref refs/remotes --format='%(authorname)%09%(refname:short)' \
     | awk -F'\t' -v n="$(git config user.name)" '$1 == n'
   ```

2. 無ければ `git config user.name` から短い名前を作り、**ユーザーに確認する。**

## コミットの単位

- **1 つのコミットに 1 つの type。** 混ざるなら分ける。
- **どのコミットで止めてもビルドとテストが通る状態にする。** 途中で壊れる履歴を作らない。
- 挙動を変えない準備（リネーム、抽出、依存の追加）は、それを使う変更より前に別のコミットにする。
- 新しい挙動とそのテストは同じコミットに入れる。`test` は既存の挙動にテストだけを足す・直すときの type である。
- lockfile や生成コードは、それを生む変更と同じコミットに入れる。
- 本文で「なぜ」を一段落で言い切れる大きさに収める。言い切れないなら分ける。

## コミットメッセージ

```
docs: プロジェクトの目的を README に記載

PoC としての位置づけが口頭でしか共有されておらず、新しく参加した人が
本番相当の品質を求めて手戻りしていたため明文化した。

Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>
```

- **件名** — Conventional Commits 形式に倣い、`<type>(<scope>): ` または `<type>: ` に続けて
  何をしたかを簡潔に述べる。scope の付け方は type と scope 節に従う。文末に句点は打たない。
- **本文** — **何を変えたかではなく、なぜそう変えたかを書く。** 差分を読めば分かることを繰り返さない。
  簡潔に書き、1 段落程度に収める。詳しい経緯は PR 本文に譲る。
- **フッタ** — AI が作成したコミットには `Co-Authored-By:` を付ける。
  署名はエージェントの実行環境が指定する形式に従う。
  issue はコミットではなく PR 本文で閉じる。書き方は github-convention スキルに従う。

## セルフチェック

### ブランチを切る前

- 既定ブランチをコマンドで検出したか。そのブランチ上で作業していないか
- `<ユーザー名>` は、その人の既存ブランチと揃っているか
- AGENTS.md を読んだか。上書きされた項目を、既定値のまま適用していないか

### コミットする前

- 複数の type が混ざっていないか。このコミットで止めてもビルドとテストが通るか
- scope は履歴の既存の語と揃っているか。一語で特定できないのに無理に付けていないか
- 言語は既存の履歴と揃っているか
- 本文は「なぜ」を書いているか。差分の説明になっていないか
