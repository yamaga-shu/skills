引数: $ARGUMENTS

引数の先頭の数字を issue 番号として扱う。無ければ、始める前にユーザーに聞く。

開始前に Skill ツールで "grilling"、"git-convention"、"github-convention"、"doc-convention" を 1 つずつ読み込む。
同じセッションで既に読み込んだものは読み直さない。1 回の呼び出しに複数の名前を渡さない。

- grilling が確認の聞き方（ラウンドの書式、事実は自分で調べる）を決める
- git-convention がブランチ名、コミットの単位、コミットメッセージの書き方を決める
- github-convention が issue の読み方、本文の改訂の仕方、コメントの投稿の仕方を決める
- doc-convention がドキュメントの変更をどこに置くかを決める

## grill-with-docs との分担

grill-with-docs は「どう作るか」を決め、issue の「決定」「設計」に残す。
このスキルは、決まったことを「どの順に、どのコミットで作るか」に落とす。
設計の質問はしない。issue の「決定」「設計」が計画を立てるのに足りなければ、
足りない論点を挙げて `/grill-with-docs <番号>` を案内し、計画を止める。

## issue を読む

github-convention の「issue の読み方」に従って本文とコメントを読む。

- 「決定」「設計」「スコープ」は確定した前提として扱い、聞き直さない
- 「実装時に決めること」「注記」は、計画に影響するものだけを確認の候補にする
- コメントの改訂の記録を読み、本文の現在の文がどの経緯で決まったかを把握する。
  先行するセッションの「実装計画」コメントがあれば、それを出発点にする
- sub-issue を持つ issue は PR を持たないので計画の対象にしない。どの sub-issue を計画するかをユーザーに聞く
- 本文が ISSUE-FORMAT.md の構成でなければ、本文全体から「何を作るか」と「完了条件」を読み取り、
  読み取れない部分を確認の候補にする

## リポジトリの状態を読む

計画の起点を決めるために、次を確認する。

```bash
git branch --show-current
git status --short
git fetch --prune
```

- 対応する PR は、issue を読んだときの `closedByPullRequestsReferences` で知る。
  PR があれば `gh pr view <PR番号> --json headRefName` でブランチを得る
- PR が無ければブランチ名で探す。AGENTS.md の「Git 規約」で上書きされた形式も含め、
  実際に使われているブランチ名の形式に issue 番号が入るときだけ `git branch -a | grep '/<番号>/'` を使う。
  入らない形式なら名前では探せないので、既存ブランチの有無を確認の候補にする
- issue に対応するブランチや PR が既にあれば、そのブランチのコミットを `git log` で読み、続きを計画する。作り直さない。
  PR があれば、その番号を計画の「ブランチ」に書く
- 未コミットの変更があれば、計画の対象と重なるかを見て、扱いを確認の候補にする
- ブランチ名の `<ユーザー名>` は git-convention の手順で決める。決まらなければ確認の候補にする

## コードを調べる

issue の「設計」と「含む」に挙がったものについて、変更が及ぶファイルとその周辺を読む。
規模が大きければサブエージェントに調べさせ、報告を待つ間に確認のラウンドを進める。

- ビルド・テスト・lint のコマンド。AGENTS.md、README、設定ファイルから拾う。各コミットで通すべきものになる
- 既存のテストの置き場所と書き方。新しいテストはそれに揃える
- issue の「設計」が前提とするコードの構造が、実際にそうなっているか。食い違いがあれば確認の候補にする
- 変更行数の見積もり。github-convention の分割の基準を超えそうなら、計画を止めて分割を提案する。
  分割は github-convention の sub-issue の手順、または `/grill-to-issue` で行い、分割後の一つの issue を改めて計画する
- README、用語集、ADR に影響するか。影響すれば doc-convention の正本の表に従って場所を決め、
  `docs` のコミットとして計画に含める

## 確認する

聞くのは、答えによって計画の構成（コミットの分け方、変更するファイル、起点）が変わる事柄だけである。

- issue の「設計」とコードの実態の食い違い
- 「実装時に決めること」のうち、答えで計画の構成が変わるもの。変わらないものは聞かず、計画に推奨案を書く
- 環境、権限、外部リソースなど、調べても分からない前提
- 既存ブランチや未コミットの変更の扱い
- ブランチ名の `<ユーザー名>`

質問は grilling のラウンドの書式で、推奨する答えを添えて聞く。事実は自分で調べ、ユーザーに聞かない。
通常は 1 ラウンドで済む。答えによって新たな確認が生じたときだけ次のラウンドを聞く。
確認することが無ければ、ラウンドを挟まずに計画を提示する。

## 計画を立てる

[PLAN-FORMAT.md](./PLAN-FORMAT.md) の構成で書く。
このファイルは自動では読み込まれないため、計画を書く前に必ず読むこと。

- コミットは git-convention の「コミットの単位」に従って分け、件名はコミットメッセージの書式で書く
- 各コミットに「なぜそう変えるか」を一段落で添える。実装時にコミット本文にそのまま使う
- 「完了条件」の各項目に、確かめ方を対応させる
- 計画は手順書でよい。ただし issue の本文に書かれていることを書き写さず、参照する

## 提示と記録

計画の全文を提示し、ユーザーの承認を得る。承認前に issue に書かない。

承認されたら、次の順で issue に残す。本文の受け渡しは github-convention に従いヒアドキュメントで行う。

1. 確認の結果、issue の「決定」「設計」「スコープ」を変えた点があれば、
   github-convention に従って本文を編集し、改訂のコメントを残す
2. 計画を `gh issue comment <番号> --body` で投稿する。
   実装が別のセッションになっても、issue を読めば計画に達せるようにするため。
   「実装時に決めること」への回答は issue 本文には書かず、計画の中に残す。
   PR を作るときに本文の「検討したこと」へ写す
3. 計画を作り直したときは新しいコメントを投稿する。実装者は最新の「実装計画」コメントを使う

## 実装への動線

記録したら、このまま実装に進むかをユーザーに聞く。

- 進むなら、Skill ツールで "implement-from-issue" を読み込む。このとき args に issue 番号を渡す。
  承認した計画からこのセッションで続け、issue とコードは既に読んでいるので読み直さない
- 進まないなら、ブランチ名と最初のコミットの件名を示して終える。
  実装は後で `/implement-from-issue <番号>` から始められる
