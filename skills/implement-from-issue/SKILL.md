引数: $ARGUMENTS

引数の先頭の数字を issue 番号として扱う。
引数が無くても、このセッションで plan-from-issue の計画を承認したばかりなら、その issue の番号を使い、ユーザーに聞き直さない。
どちらも無ければ、始める前にユーザーに聞く。

開始前に Skill ツールを 3 回呼び、"git-convention"、"github-convention"、"doc-convention" をこの順にそれぞれ読み込む。
同じセッションで既に読み込んだものは読み直さない。1 回の呼び出しに複数の名前を渡さない。

- git-convention がブランチの切り方、コミットの単位、コミットメッセージの書き方を決める
- github-convention が PR の書き方と、issue 本文の改訂の仕方を決める
- doc-convention がコメント・docstring・ドキュメントの書き方を決める

## 計画を手に入れる

- このセッションで plan-from-issue の計画を承認したばかりなら、その計画から始める。issue とコードを読み直さない
- そうでなければ `gh issue view <番号> --json title,body,comments` で本文とコメントを読み、
  最新の「実装計画」コメントを計画とする。
  `--comments` は非対話環境ではコメントだけを出力し本文が落ちるため使わない。
  計画のコメントが無ければ `/plan-from-issue <番号>` を案内して止める。計画無しに実装を始めない。
  計画の投稿後に本文の改訂コメントがあれば、計画がその改訂を織り込んでいるかを確かめ、
  織り込んでいなければユーザーに指摘してから進める

## ブランチを切る

計画の「ブランチ」に従う。git-convention の「ブランチを切る前」のセルフチェックを通す。

- 既定ブランチから切るときは、リモートの最新を取り込んでから切る
- 既存ブランチの続きなら、そのブランチに移り、計画に書かれたコミットが入っていることを `git log` で確かめる
- 未コミットの変更が残っていれば、計画で決めた扱いに従う。計画に無ければユーザーに聞く

## コミット単位で実装する

計画の「コミット」を上から順に進める。コミットごとに次を繰り返す。

1. 変更を書く。コメント・docstring は doc-convention に従う
2. 計画に添えた確認コマンドを通す。無ければリポジトリのテストと lint を通す
3. 計画の件名と理由でコミットする。フッタは git-convention に従う

計画は承認済みなので、コミットごとにユーザーの承認は求めない。ただし次のときは止めてユーザーに問う。

- 計画どおりに作れないと分かった。前提としたコードの構造が違う、テストが通らない原因が計画の外にある、など
- コミットの分け方や変更するファイルを計画から変えたくなった
- issue の「決定」「設計」を変える必要が出た。変えると決めたら、github-convention に従い本文を編集し改訂コメントを残す

計画から外れずに済む小さな判断（命名、置き場所など）は自分で決め、PR 本文の「検討したこと」の材料として控えておく。

## 完了条件を確かめる

全コミットを終えたら、計画の「確認方法」を一つずつ実行し、結果を控える。
満たせない完了条件があれば、PR を作る前にユーザーに報告する。

## PR を出す

タイトルと本文の全文を提示し、ユーザーの承認を得てから push と `gh pr create` を行う。承認前に push しない。

- タイトルと本文は github-convention の PR-FORMAT.md に従う。本文はヒアドキュメントで渡す
- 「検討したこと」には、計画の「実装時に決めること」、実装中に決めたこと、計画から外れた点とその理由を書く
- 「確認方法」には、実行した確認とその結果を書く
- 末尾は `Closes #<番号>` を 1 つだけ書く
- レビューに出せる状態でなければ `--draft` を付け、何が残っているかを本文に書く

PR の URL を示して終える。
