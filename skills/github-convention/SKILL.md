# GitHub 運用規約

AI エージェントが GitHub 上の issue と PR を扱う際に従う規約。
人間の運用を縛るものではなく、AI に一貫した振る舞いをさせることを目的とする。

## 前提

- **言語**は git-convention スキルの「前提」に従う。正本はそちらで、ここには書かない。
  まだ読んでいなければ、Skill ツールで "git-convention" を読み込む。
- **設計の検討の経緯の正本は issue** とし、設計書をリポジトリに md ファイルとして置かない。
  正本の分担は doc-convention スキルの「正本の表」に従う。
- リポジトリに `.github/ISSUE_TEMPLATE/` や `.github/PULL_REQUEST_TEMPLATE.md` があれば、
  節の構成はそちらを優先し、本スキルのテンプレートは書く内容の指針として使う。

## Issue

- タイトルは、その issue で何を達成するかを述べる。`<type>: ` は付けない。
- 本文は [ISSUE-FORMAT.md](./ISSUE-FORMAT.md) の構成に従って記述する。
  このテンプレートは自動では読み込まれないため、issue を作る前に必ず読むこと。
- **手順書ではなく、判断とその根拠を残す場所として書く。** 実装者が「なぜこうするのか」を問い直さずに済むことを目指す。
- 判断が割れうる論点は、採らなかった選択肢との比較を表で残す。
- **実装を伴う issue は 1 つの PR で閉じる。** issue と PR を 1 対 1 に対応させ、
  1 つの PR で閉じられない大きさなら issue の側を分割する。
- **粒度は、一つの目的を数行のリード文で言い切れ、完了条件を外から判定できる単位にする。**
  この質的な基準を主とし、量の上限として、人が書いて人が読む変更行数（追加と削除の合計）の
  見積もりが 2000 行を超えそうなら分割する。
  lockfile、生成コード、フィクスチャ、フォーマッタだけの変更、単純なリネームは数えない。
  2000 行は目標値ではなく分割を検討するトリガーである。
  逆に 200 行でも無関係な目的が混ざっていれば分ける。
- **分割は親 issue と sub-issue で表す。** 元の issue を親とし、分割先を GitHub の sub-issue として結ぶ。
  「関連: #番号」のような本文のリンクで代用しない。
  - 新しく分割先を作るときは `gh issue create --parent <親の番号>`、
    既存の issue を結び直すときは `gh issue edit <親の番号> --add-sub-issue <番号>,<番号>` を使う。
  - 親 issue は PR を持たない。sub-issue がすべて閉じたら親を閉じる。
  - 親 issue の本文には、分割の前に固めた「決定」と「含まない」を残し、
    「完了条件」は sub-issue がすべて閉じていることとする。
    sub-issue の一覧は GitHub が親に表示するため、本文に書き写さない。
  - sub-issue の本文は通常の issue と同じ構成で書く。親の「決定」は前提として扱い、書き写さず参照する。
- **設計に改訂が生じたら、本文を編集して正本を最新に保つ。**
  読み手が本文だけで現在の設計に達せるようにし、コメントを遡らないと分からない状態を作らない。
  本文の編集は `gh issue view <番号> --json body -q .body` で現在の本文を取り出し、
  改訂する箇所だけを変えて `gh issue edit <番号> --body` で書き戻す。改訂しない箇所を書き換えない。
- **改訂の記録は、改訂した箇所だけをコメントに残す。**
  本文が最新で、コメントが履歴。全体像や変えていない部分をコメントに積み直さない。
  コメントには、改訂した節と、何をどう変えたか、その理由を書く。

  ```markdown
  ## 改訂: 決定「セッションの有効期限はサーバ側で管理する」

  - 変更前: 有効期限はクライアントが JWT の exp で判定する
  - 変更後: サーバ側のセッションストアで管理し、クライアントは判定しない
  - 理由: 失効を即時に反映する要件が加わり、クライアント判定では満たせないと分かったため
  ```

## issue の読み方

本文とコメントは次で読む。
`--comments` は非対話環境ではコメントだけを出力し本文が落ちるため使わない。

```bash
gh issue view <番号> --json title,body,comments,parent,subIssuesSummary,closedByPullRequestsReferences
```

- 親 issue（`parent`）があれば本文も読み、親の「決定」と「含まない」を前提に加える
- `closedByPullRequestsReferences` が、その issue を閉じる PR である。本文の全文検索で PR を探さない。
  同じ数字を含む無関係な PR を拾うため
- 実装計画は、コメントのうち最新の「## 実装計画」である
- 本文が ISSUE-FORMAT.md の構成でなければ、本文全体から読み取る

## PR

- タイトルは、その PR が何を成し遂げるかを簡潔に述べる。
  1 つの PR に複数の type のコミットが入りうるため、コミットメッセージと違い `<type>: ` は付けない。
- 本文は [PR-FORMAT.md](./PR-FORMAT.md) の構成に従って記述する。
  このテンプレートは自動では読み込まれないため、PR を作る前に必ず読むこと。
- 対応する issue は、本文末尾の `Closes #<番号>` で閉じる。個々のコミットには書かない。
  issue と PR は 1 対 1 なので、`Closes` は 1 つだけ書く。親 issue を `Closes` しない。
- **一度実行すればもう繰り返されない操作は、叩いたコマンドを本文の「実行したコマンド」節に残す。**
  実行記録は、それが行われた PR に紐づいているときに最も文脈が揃う。

## gh コマンドでの本文の受け渡し

`gh issue create` / `gh issue edit` / `gh pr create` / `gh issue comment` など本文を伴うコマンドでは、
一時ファイルに書いて `--body-file` で渡さず、**ヒアドキュメントでコマンド内に直接埋め込む。**

```bash
gh issue create --title "バッチ処理の実行環境を Docker で構築する" --body "$(cat <<'EOF'
本文をここに書く。
EOF
)"
```

開発者が、実行されるコマンドそのものから本文を読めるようにするため。
ファイル経由だと承認を求められた時点で中身が見えない。

区切り子は変数展開とコマンド置換を防ぐため `'EOF'` とクォートする。

## セルフチェック

issue や PR を作る前、コメントを投稿する前に、以下を自問する。

- タイトルに `<type>: ` を付けていないか
- issue 本文は手順書になっていないか。判断とその根拠が書かれているか
- issue に複数の目的が混ざっていないか。変更行数の見積もりが 2000 行を超えていないか
- 分割を本文のリンクで済ませ、sub-issue で結んでいない issue はないか
- 1 つの PR で複数の issue や親 issue を `Closes` していないか
- その issue を閉じる open な PR が既に無いか。あれば新しい PR を作らず、その PR を更新しているか
- 設計の改訂を、本文を編集せずコメントだけで済ませていないか
- `Closes` を PR 本文ではなくコミットに書いていないか
- 本文をファイル経由で渡していないか
